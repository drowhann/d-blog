# Vibe Coding a Nuxt SQL Inspector

<br>

I mostly use Drizzle. It already has a logging feature, so the SQL is right there. The problem is where it shows up: a pile of queries in the terminal. Matching a log line to the request that fired it, spotting duplicates, telling sequential from parallel - all of that is painful when you are scrolling a terminal.

I wanted Django Debug Toolbar / Laravel Telescope for Nuxt: open a page, see the request, see the SQL. Not a generic query log. Which HTTP call fired which queries, how long they took, and whether they ran in parallel or one after another.

So I built [nuxt-sql-inspector](https://github.com/drowhann/nuxt-sql-inspector). And yes, I mostly vibe coded it. This post too, happily.

<br>

## The idea

Nuxt already has DevTools. What it does not have is a first-class "this request ran these queries" view. I did not want to patch Prisma, Drizzle, and every other ORM. SQL always goes through a driver. Wrap the driver once and everything above it shows up - including Drizzle, if you wrap `db.$client` or the pool you pass in.

That is the whole product:

1. Wrap `pg`, `postgres.js`, `mysql2`, libSQL, `better-sqlite3`, or db0 with `inspectSql()`.
2. Attach those queries to the current Nitro request.
3. Show them at `/__sql_queries` and in a DevTools tab.

```ts
import { inspectSql } from 'nuxt-sql-inspector/node-postgres'

const pool = inspectSql(new Pool({ connectionString }))
```

No auto-patching. You wrap the client you already create. When the module is off, those imports are a no-op.

<br>

## What "vibe coded" actually meant

I did not sit down and type a Nuxt module from a blank `src/module.ts`. I pointed Cursor at the problem, described the UI I wanted, and iterated.

That is a good way to get a playground, a wrap API, and a request list on the screen. It is a bad way to ship a published module if you stop there.

The agent will happily use Nuxt auto-imports (`defineEventHandler`, `onMounted`, `definePageMeta`) as if the code still lives inside an app. In `node_modules` those macros are gone. First published versions threw `defineEventHandler is not defined`. `definePageMeta` is a compile-time macro, so it also died in `dist/`. Fix was boring and specific: explicit imports from `h3` / `vue` / `nuxt/app`, and disable the layout from `extendPages` instead of the page.

Same story for pool checkouts. Wrapping `pool.query` is easy. Wrapping `pool.connect()` / `getConnection()` so transactions still record, without double-counting the inner client, is the kind of edge the first prompt misses.

Vibe coding got me the shape. Reviewing the published package, the driver wraps, and the "this must never run in production" path is what made it real.

<br>

## What shipped

Dev-only by default. Params redacted unless you turn that off. Slow queries highlighted. Duplicate SQL on a request gets a `×N` badge. A waterfall so you can see overlap vs sequential.

It works on Nuxt 3 and Nuxt 4. Install:

```bash
pnpm add -D nuxt-sql-inspector
```

```ts
export default defineNuxtConfig({
  modules: ['nuxt-sql-inspector'],
})
```

Open `/__sql_queries` while `nuxt dev` is running.

More on the [project page](/project/nuxt-sql-inspector), or the [repo](https://github.com/drowhann/nuxt-sql-inspector).
